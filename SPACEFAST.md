# Spacefast migration (local preparation only)

The Cloudflare build remains `npm run build` (`dist/`). The separate `npm run build:spacefast` uses `@spacefast/astro/adapter@0.4.1`, writes to `dist-spacefast/`, and records classification in `.spacefast/build.json`. `sf.jsonc` declares the generated Functions entry and database capability, but neither build command publishes anything. The generated manifest is ignored; do not publish just `client/` because the 50 instrument pages need the Functions server entry for URL-state HTML. Never archive or publish the repository root: `.dev.vars`, `.env*`, migration exports and credentials must stay out of uploads. Exclude the existing `public/.DS_Store` from a publish artifact too. Determine a scoped publish plan that includes the manifest, server and client assets without source secrets before requesting publish approval.

Spacefast's adapter passes request-local bindings as `Astro.locals.runtime.env`; Cloudflare Astro 7 uses `cloudflare:workers` instead. The target-specific modules keep the Cloudflare import out of the Spacefast server bundle. The Spacefast request board and write APIs currently return 503 unless `PRIMITIVES_SPACEFAST_BACKEND_READY=verified`, a Spacefast-only runtime variable. Do not set it merely because the build passed. The backend also refuses missing `DB`, `VOTE_SALT` or forwarded visitor address; there is no production fallback salt or shared `local` identity. `VOTE_SALT` must remain a secret and continuity with existing votes requires its old value to be provisioned securely. A changed salt makes existing voter hashes incomparable.

After building, `npm run check:spacefast` checks generated route facts, nondefault-query HTML and disabled backend responses. `npm run preview:spacefast` serves only built client files and delegates other requests to the built handler on `127.0.0.1:4398`; it has no database and does not model Spacefast's hosted ingress or asset routing.

Release gates before enabling that variable:

1. Confirm the generated `.spacefast/build.json` route classification and Functions entry are accepted by a private hosted version; confirm assets are served from `client/`, never server files. The documented `sf dev` does not emulate Functions. Build and local handler checks are not proof of hosted operation.
2. Test the real `env.DB` broker against disposable data, including numbered/repeated `?1` binds, `first`, `run`, `batch`, `INSERT OR IGNORE`, `unixepoch()`, `ON CONFLICT ... RETURNING`, and transactions/atomic vote counting. Spacefast documents a MySQL-backed D1-shaped broker but not these SQLite semantics. The applied D1 migrations must not be reused as MySQL schema. Develop separate compatible schema and SQL only against observed behavior.
3. Confirm the ingress strips visitor-supplied `x-forwarded-for` and supplies a trusted first hop. The adapter uses that first hop as `clientAddress`; test spoofed headers on a private version before counting votes. Test same-origin, honeypot, rate limits, repeated votes and the subscriber/request flows against compatible disposable storage.
4. Check nondefault URL parameters on an SSR tool, `/requests`, a row fragment and every API. Confirm `VOTE_SALT` is present only in runtime bindings, never in published assets or build logs. Stage/transfer production records only after a separately approved data plan.

Cutover requires separate approval to publish, provision secrets/data, and change DNS. Keep the Cloudflare Worker and D1 intact until hosted checks pass. Preserve the current apex and www/design redirect behavior; obtain exact Spacefast A/AAAA/TXT records, do not guess a CNAME. Rollback is to restore the previous Cloudflare DNS routing and the existing Cloudflare build/Worker, retaining the D1 database and secret throughout. No deployment, DB transfer or DNS change is part of this preparation.
