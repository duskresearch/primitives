# Spacefast site with Cloudflare business API (local preparation only)

The default `npm run build` remains the Cloudflare site (`dist/`). `npm run build:spacefast` writes the full 50-instrument Astro site to `dist-spacefast/` with the Functions entry and `client/` assets. `sf.jsonc` declares `database: false` and `fetch: true`: Spacefast needs no database, MySQL connection, or vote salt. Neither build publishes anything. Never upload the repository root, `.dev.vars`, `.env*`, migrations, or credentials. A future scoped artifact must include the generated manifest, server and client assets, while excluding `public/.DS_Store`.

The existing D1 database, SQLite schema and `VOTE_SALT` stay on Cloudflare. `workers/business-api/` is a separate Worker with only five authenticated operations: board, row, request, vote and subscribe. There is no arbitrary SQL endpoint. The default site calls the same business operations directly through its D1 binding; the Spacefast build signs a time-bound request envelope using `PRIMITIVES_BRIDGE_KEY` and calls a fixed HTTPS `PRIMITIVES_BACKEND_ORIGIN`. The backend independently requires the signature, public origin, operation, method, trusted visitor address, DB, salt and configured `PRIMITIVES_PUBLIC_ORIGIN`. Its config has no public route or workers.dev host. Provisioning the same existing salt at a later authorized cutover preserves voter hashes; a new salt would change visitor identity.

New subscriber rows created through the Spacefast bridge have `country: null`: no trusted visitor-country metadata is forwarded. Existing subscriber rows and their country values remain untouched.

The Spacefast runtime still requires `PRIMITIVES_SPACEFAST_BACKEND_READY=verified` to use the bridge. Leave it unset until a private hosted spoofed-XFF test proves that Spacefast strips caller-supplied `x-forwarded-for` and its first hop represents ingress. The local preview cannot prove this. Never set the ready gate merely because tests or builds passed. Configure the bridge key separately as a secret on both targets, the backend origin only on Spacefast, and the public origin only on the backend. No real keys are in this repository.

For local review, run `npm run build:spacefast` then `npm run preview:hybrid`. The preview listens only on `127.0.0.1:4400`, uses a synthetic key/salt and a fresh disposable Miniflare D1 database, and routes the built site's signed requests to the bundled backend Worker in workerd. Data vanishes on shutdown. It does not emulate Spacefast's hosted ingress, DNS, fetch capability, or asset routing. `npm run preview:spacefast` on 4398 remains the disabled-backend artifact check. The business API package check is `./node_modules/.bin/wrangler deploy --config workers/business-api/wrangler.jsonc --dry-run --outdir /private/tmp/primitives-business-api-dryrun --no-autoconfig`; dry-run is not a deploy. Tests use synthetic D1, and no live DB connection is needed.

Before any release, request separate approval to publish, provision secrets, attach a private API host, perform hosted ingress and SSR checks, transfer any data (not required for this D1-preserving approach), or change DNS. Verify `.spacefast/build.json` route classification and assets on a private hosted version, then test spoofed XFF, all writes and shared URL state against disposable hosted storage. Keep the existing Cloudflare site Worker and D1 intact for rollback. Obtain exact DNS records rather than guessing them. No deployment or cutover is part of this preparation.
